### 🔶 Advisory

- **[Quality]** `src/gavel_ai/models/config.py:293` — `EvalConfig.tuning`'s field description states "(required when workflow_type='autotune')" but, unlike `ConversationalConfig` (enforced via `validate_conversational_config`, `config.py:296-304`), no `model_validator` enforces this — an `autotune` config without a `tuning` block parses successfully (confirmed by `test_eval_config_tuning_defaults_to_none`, which exercises the `oneshot` path but not an `autotune`-without-`tuning` case). Neither `tech-design.md` nor `approach.md` explicitly call for this validation, so it is not a spec-conformance gap, but the description text creates an expectation the model doesn't enforce — recommend either softening the description to "typically required" or adding a validator mirroring `validate_conversational_config` (can be deferred to whichever partition first instantiates `AutotuneWorkflow`, since nothing yet consumes `EvalConfig.tuning`).
- **[Arch Violation — minor]** `src/gavel_ai/core/contexts.py:741-751` — `IterationEvalContext.get_prompt()` looks up only `data.get(self._version)`, while the ADR-AT-2 reference implementation also normalizes `v`-prefix variants (`data.get(self._version) or data.get(f"v{version_key}")`) and splits `prompt_ref` defensively. Functionally equivalent for the documented call pattern (`version` is always constructed as `f"v{iteration}"` by `AutotuneIterationStep`), and the simpler form is arguably cleaner — but worth a one-line note to Partition 2 authors that `version` must always be passed in canonical `"vN"` form.
